The aim of this project is to test a single hypothesis. ELFuzz produces seed inputs \textit{indirectly}: it uses an LLM to synthesise generation-based fuzzers, and those fuzzers are then run to emit the inputs \cite{chen_2025_elfuzz}. \toolname{} removes the intermediate program and asks the LLM for the inputs directly. Our conjecture is that this is a \textbf{more direct route to diverse, semantically interesting inputs}, and therefore to \textbf{more varied coverage of the system under test (SUT)} -- which is ultimately what a fuzzing campaign is trying to achieve. By eliminating the generator, the model's knowledge of the input format is spent on the inputs themselves rather than on writing a program that happens to produce them, and coverage feedback selects directly over the objects we care about.

This chapter sets out how we test that hypothesis. The whole evaluation is framed as a like-for-like comparison between \textbf{\texttt{elfuzz synth}} (the original, generator-synthesising pipeline) and \textbf{\texttt{elfuzz direct}} (our input-generating modification), run under identical models, hardware, and time budgets. We describe the research questions (Section~\ref{sec:eval-rqs}), the experimental setup and protocol (Section~\ref{sec:eval-setup}), and the metrics and result tables/figures that will carry the comparison (Section~\ref{sec:eval-results}). Quantitative analysis and discussion are deferred until the full set of runs has completed.

\section{Aims and Research Questions}
\label{sec:eval-rqs}

We restate the central hypothesis as the lens through which every result is read:

\begin{quote}
\textit{Generating inputs directly with an LLM yields a more diverse, more semantically interesting seed corpus -- and hence more varied SUT coverage -- than synthesising fuzzers that generate those inputs.}
\end{quote}

We decompose this into three research questions. The numbering mirrors ELFuzz's own evaluation, where RQ1 concerns input-generation effectiveness and RQ2 concerns downstream bug-finding \cite{chen_2025_elfuzz}.

\begin{itemize}
    \item \textbf{RQ1 (seed quality).} How much SUT coverage does each tool's seed corpus achieve \textit{on its own}, before any mutation fuzzing? This measures the raw quality of what each approach produces, and is the most direct test of the hypothesis: if directly generated inputs are more varied, they should cover more of the SUT.
    \item \textbf{RQ2 (downstream fuzzing).} When the seed corpus is used to bootstrap a grey-box mutation fuzzer (AFL++ \cite{bhme_2016_coveragebased,serebryany_2016_libfuzzer}), how does coverage grow over the campaign, and where does it end? A more diverse corpus should let the fuzzer past shallow checks sooner and reach a higher plateau.
    \item \textbf{RQ3 (search behaviour).} How does coverage evolve \textit{during} synthesis versus during pool evolution, and how does the corpus size behave -- in particular, does \toolname{} exhibit the consolidation behaviour predicted in Section~\ref{sec:population}, where the pool can shrink while coverage only increases?
\end{itemize}

\subsection{Configurations compared}

The two configurations are \texttt{elfuzz synth} and \texttt{elfuzz direct}. To isolate the effect of the design difference, every other factor is held fixed: both use the same code-completion LLM (Qwen2.5-Coder-1.5B, the small local model chosen to fit the available GPU), run on the same single-workstation host, and are given identical time budgets. Both pipelines end by feeding their seed corpus to the same AFL++ configuration, so any downstream difference is attributable to the seeds rather than to the fuzzer.

\subsection{Protocol}
\label{sec:eval-protocol}

Each SUT is run end-to-end through the same four-stage pipeline for both tools:

\begin{enumerate}
    \item \textbf{Synthesis / evolution (6\,h).} \texttt{synth} evolves a population of generators; \texttt{direct} evolves the input pool of Chapter~\ref{ch:project} (\toolname). Both are given a 6-hour wall-clock budget.
    \item \textbf{Corpus production.} For \texttt{synth}, a separate \texttt{produce} step runs the evolved elite fuzzers for \textbf{200\,seconds in total}, which is already sufficient to emit well over one million candidate inputs. \texttt{direct} has no \texttt{produce} step: its evolved pool \textit{is} the corpus. Both corpora are then minimised to remove inputs that are redundant for coverage.
    \item \textbf{Seed-coverage benchmark (RQ1).} The minimised corpus is executed against the SUT and the total coverage it reaches is recorded.
    \item \textbf{AFL++ campaign (6\,h, RQ2).} The minimised corpus seeds a 6-hour AFL++ campaign (one repetition in the current runs), and coverage is logged over time.
\end{enumerate}

\textbf{Instrumentation caveat.} The coverage counts produced during synthesis/evolution and the \texttt{edges\_found} reported by AFL++ come from different instrumentation, so the two phases are \textit{not} directly comparable in absolute terms. We therefore only ever compare \texttt{synth} against \texttt{direct} \textit{within} a single metric, never across the synthesis and AFL phases.

\subsection{Metrics}

\begin{itemize}
    \item \textbf{Seed coverage} -- edges covered by the minimised seed corpus alone (RQ1).
    \item \textbf{AFL coverage over time} -- \texttt{edges\_found} as a function of wall-clock time, and the final value at 6\,h (RQ2).
    \item \textbf{Bitmap coverage} -- AFL's percentage of the coverage bitmap exercised, at end of campaign.
    \item \textbf{Throughput} -- total executions and executions per second, as a sanity check that campaigns are comparable.
    \item \textbf{Corpus size} -- number of seeds, and (for \texttt{direct}) the pool size across generations, to evidence the consolidation behaviour (RQ3).
    \item \textbf{Evolution coverage} -- union of edges covered by the whole population/pool per generation, during synthesis (RQ3).
    \item \textbf{Crashes and hangs} -- saved crashing and hanging inputs found by the campaign.
\end{itemize}

\section{Threats to Validity}
\label{sec:eval-threats}

We note the following limitations, to be expanded once results are in. The AFL++ campaigns currently use a \textbf{single repetition} per configuration, so per-run variance from the stochasticity of fuzzing is not yet quantified; multiple repetitions are planned where the time budget allows. Both tools use a \textbf{small local model}, which bounds the quality of generation for both; a larger model could change the absolute numbers, though the relative comparison should hold. The evaluation covers a \textbf{subset of SUTs} and so may not generalise to all input formats. Finally, as noted in Section~\ref{sec:eval-protocol}, synthesis-phase and AFL-phase coverage use different instrumentation and must not be compared across phases.
